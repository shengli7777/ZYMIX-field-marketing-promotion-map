# ZYMIX 地推点位工作台

我结合做地推时的选址、排班和反馈流程做了这个网页。主要使用场景在伦敦，也保留了其他英国城市的地点录入。

## 使用流程

1. 登录工作台，选择已有地点，或填写城市、地点名称和可选的街道／邮编。
2. 点击查找地图位置，核对结果后选择并保存。地图会显示确认的位置。
3. 按现场观察填写四项初筛评分，记录场地确认状态。
4. 场地已确认、点位未暂停时，可以安排试推，填写日期、开始时间、人数、时长、负责人和备注。
5. 活动结束后填写反馈，可以选择对应排班，也可以补录独立活动。

地点、评分、场地状态、暂停／重启、排班和反馈都保存到 Supabase。保存成功后会提示；失败时保留表单或恢复原值。关联排班的反馈保存后，排班在页面上转为已反馈，不会重复作为待开展活动显示。

一组一场填写一条反馈。同一天、同一区域的两个独立小组，通过不同推荐码分别记录。成本或扫码数未知时留空，确实没有才填 0。两人各工作两小时，就是 4 人时。

## 演示和团队数据

未登录时显示模拟活动，修改仅在本次页面有效。登录后只读取团队保存的地点和活动。已移除 A–D 四个内置客流候选点；本次更新不删除数据库记录。

## 本次升级

先在 Supabase SQL Editor 中完整运行 `workflow-update.sql`，成功后替换网页文件。脚本增加字段、排班表和排班反馈关联，不删除已有地点或反馈。之前的 `location-update.sql` 已运行过就不用重复操作。

网页文件是 `index.html`、`style.css`、`app.js` 和 `cloud.js`，需放在同一目录。用 VS Code 的 Live Preview 打开 index.html，确认通过后再发布 GitHub Pages。

## 后台和权限

登录账号必须加入 team_members，成员可以查看团队数据。成员名单不能从网页自行修改。排班的场地状态在数据库侧也会检查。网页不提供删除数据功能。

cloud.js 中的 publishable key 是浏览器连接配置，数据保护依赖数据库授权和 RLS。数据库密码、secret key 和 service_role 不能提交到公开仓库。真实活动数据也不应写进代码。

## 目前的限制

刷新页面后需要重新登录。数据不会实时推送，重新登录可以读取团队最新记录；多人同时修改同一字段时，以最后一次提交为准。排班目前支持新建和关联反馈，尚未提供编辑或取消入口。程序测试覆盖了请求、数据转换和错误处理，部署后仍应实际验证一次保存与重新登录读取。

地点查询使用 Photon 公共演示服务，只在点击时请求，并缓存同一查询；允许适度使用但不保证可用性。规模扩大后需要有服务保障的查询接口或自建服务。文档：https://github.com/komoot/photon 。地图和位置数据来自 OpenStreetMap，候选结果需人工确认，系统不会自行猜测正确地点。
